# Amem

给编码 agent 用的跨会话记忆。两个文本文件加标准库。

Amem 记住 agent 对用户和项目学到的东西，把其中该常驻的部分不问自动带进每一次后续对话，其余的留给检索。它是一个库，不是一个服务：没有守护进程，没有向量数据库，没有嵌入模型，除了 Python 本身什么都不用装。

---

## 为什么会有这个东西

多数记忆库就是一个向量库加一次检索调用：你问，它找。这答好了一类问题，留下两个没解决的。

**有些记忆永远不会被问起。** "对外文档里不许出现函数名"是靠**不做某件事**来遵守的。没有人会输入一个能检索到它的查询，而一个只回答查询的系统永远不会把它拿出来 —— 于是这条规则正确地躺在数据库里，而 agent 照样违反它。在一位用户的真实工作记录上测了 243 条发言：**89% 是指令**（"改一下"、"跑测试"、"发版"），这些场景里根本没有检索发生，能帮上忙的只有**不请自来**的那部分。8% 在问单条已存事实。2.5% 需要组合多条。

**总得有人决定记什么。** 抽取可以**注意到**一个事实，但它不该能**写下**一个。这个领域里其余的库都是静默写入的 —— 你只有事后去翻，才知道它记了你什么。

Amem 就建在这两个回答上：记忆按"必须在场"还是"可以查阅"分开，而且**没有人点头，什么都进不了库**。

## 和开源方案的对比

调研了十个开源记忆系统，实测五个。同一份语料、同一个判分器、同样的内容喂给每一个。完整配置和复现步骤见 [`benchmarks/README.md`](benchmarks/README.md)。

空格都标了原因：**✗** 该系统的设计使这项测量无法进行 · **—** 没有跑。

### Amem 明确领先的地方

| 维度 | **Amem** | 其他方案里最好的 | 差距 |
|---|---|---|---|
| 安装体积 | **除标准库外为 0** | 360 MB 依赖树(mem0) | 其余的是 0.97–1.4 GB 环境 |
| 建库 788 轮 | **0.0 秒** | 0.1 秒（BM25，纯内存） | Cognee 约 20 分钟，SimpleMem 约 2 小时 |
| **写一条记忆再搜索** | **1.7 ms** | 两个最快的检索器**做不到** | 它们索引在内存里，必须整体重建 |
| 二十轮实付 token | **1,262** | 2,480（每轮检索注入） | 便宜一半，且随会话变长继续拉开 |
| 事实变更后答当前值 | **6/6** | 4/6(mem0) | mem0 另有 1 题答旧值、1 题并列不指明 |
| 从未变更的规则留存 | **3/3** | 1/3(mem0) | 丢掉的两条**没有任何迹象** |
| 中文召回@8（非稠密类） | **58.9%** | 49.3%（mem0 混合） | LlamaIndex BM25 是 2.3% |
| 写入需要人点头 | **是** | **没有一个有** | 其余全部静默写入 |
| 存储是可手改的纯文本 | **是** | **没有一个有** | 其余是向量库或专有格式 |
| 记忆不问也会到场 | **是** | **没有一个有** | 其余全部查询驱动 |

最后三行是设计选择而不是跑分，但它们决定的是**你能不能信任、能不能纠正、能不能靠它管住 agent 的行为**。这三样没有一个竞品提供。

### 选别的方案，你要付的代价

每一条都来自实测，不是读文档得出的。

| 系统 | 它向你收的费用 |
|---|---|
| **mem0** | 360 MB 依赖树加一个嵌入模型。建库慢 300 倍（30.5 秒对 0.0 秒），查询慢 79 倍。**2026-04 它放弃了 UPDATE/DELETE 整合改成单遍累积**，于是在事实被修订的六题里，它 1 题答旧值、1 题把新旧并列却不说哪个现行；三条从未变更的规则，它只留住了 1 条。 |
| **Cognee** | 每一次查询都是一次 LLM 调用 —— 没有本地索引可言，也就没有离线可用性、没有可预测的延迟、没有零成本查询。788 轮建库约 **20 分钟**。它召回看着高(75.4%)是因为它的“一个结果”是**二十轮的文档块**，八个结果等于 160 轮，别人是八轮。 |
| **SimpleMem** | 端到端质量最高(76.3%)，代价是建库约 **2 小时**、每次查询一次 LLM，而且**它只给答案、从不返回原文轮次** —— 你无法核对它凭什么这么答，也无法在它错的时候定位到源头。 |
| **MemOS** | 约 1.2 GB 环境、每次查询一次 LLM 调用，而端到端 **47.0%，低于纯本地的词法基线**。它的召回优势(69.5%)没有转化成答案。 |
| **txtai · LlamaIndex BM25** | 它们是**检索器，不是记忆**:没有“事实被取代”这个概念，没有类别，没有批准，索引在内存里 —— 写一条就得整体重建。BM25 在**中文上只有 2.3%**。 |
| **Graphiti · Zep · Letta · Memori · TencentDB** | 根本跑不起来，原因见下面“五个没能测成的”。 |

### 质量

召回@8 是确定性测量（答案所在的那一轮有没有被取回），302 道题。端到端准确率由 LLM 判分、120 道题，报的是多次运行的均值和区间 —— 因为**同一个系统在完全相同的条件下重复跑，能相差十个点**。

| 系统 | 召回@8 英文 | 召回@8 中文 | 端到端 | 跑数 | 区间 |
|---|---|---|---|---|---|
| mem0 — qdrant 混合 | **68.5%** | 49.3% | 52.7% | 8 | 49.2–55.8 |
| **Amem** | 64.6% | **58.9%** | 49.4% | 8 | 46.7–53.3 |
| LlamaIndex BM25 | 60.6% | 2.3% | 48.0% | 8 | 43.3–52.5 |
| MemOS | 69.5% ✻ | — 只跑了英文 | 47.0% | 2 | 43.3–50.8 |
| txtai — 稠密 + BM25 | 57.6% | 61.9% | 46.6% | 3 | 43.3–48.3 |
| mem0 — 纯向量，多语言 | 58.3% | 54.6% | — 端到端没跑 | — | — |
| BM25 + 五行中文分词 | 60.6% | 51.3% | — 这是基线不是系统 | — | — |
| *Amem，换更强的模型作答* | *— 检索相同* | *— 同上* | *54.5%* | 7 | 52.5–55.8 |

**✻** 来自 118 题子集，与 302 题各行不可直接并列。同一子集上 Amem 是 61.9%，MemOS 是 69.5%。

**Cognee 和 SimpleMem 不在这张表里**，尽管它们端到端更高 —— 64.3% 和 76.3%。它们在查询时跑自己的模型，所以那个数字量的是**它们的模型和它们的记忆合在一起**，而没有办法把模型固定住来比较。对照那一行说明了其中有多少是模型的功劳：同样的 Amem 检索，换个更强的模型作答就动了五个点，而存下来的东西一个字没变。它们的代价在下面那张表里，那里是可比的。

**Amem 在检索上处于中游。** 这张表里有两行赢它。**如果你要优化的正是这个，它不是该选的库。** 这个数字放在这里，是因为一份自己人写的对比，凡是藏起自己输的那一栏，别的栏就都不必看了。

### 代价

灌入 788 轮，查询 40 次，同一台机器。

| 系统 | 建库 | 查询中位 | 索引磁盘 | 写一条再搜索 | 安装体积 |
|---|---|---|---|---|---|
| **Amem** | **0.0 秒** | 0.5 ms | 1.0 MB | **1.7 ms** | **除标准库外为 0** |
| LlamaIndex BM25 | 0.1 秒 | **0.1 ms** | 0.7 MB | ✗ 整体重建 —— 索引在内存里 | ~970 MB 环境 |
| txtai | 1.5 秒 | 8.5 ms | 2.0 MB | ✗ 整体重建 —— 索引在内存里 | ~970 MB 环境 |
| mem0（关闭抽取） | 30.5 秒 | 39.5 ms | 3.7 MB | — 没跑；qdrant 是增量写入，本来也不该有重建 | 360 MB 依赖树 |
| MemOS | 数分钟 | ✗ 每次查询都是一次 LLM 调用 | ✗ 无本地索引 | ✗ 无本地索引 | ~1.2 GB 环境 |
| Cognee | 约 20 分钟 | ✗ 每次查询都是一次 LLM 调用 | ✗ 无本地索引 | ✗ 无本地索引 | ~1.0 GB 环境 |
| SimpleMem | 约 2 小时 | ✗ 每次查询都是一次 LLM 调用 | ✗ 无本地索引 | ✗ 无本地索引 | ~1.4 GB 环境 |

最后三行的建库发生在 LLM 里，所以它们的耗时是账单而不是跑分，和前四行不同量纲。它们的查询延迟和索引大小标 ✗ 也是同一个原因：没有本地索引可计时、可测量，而给一次网络往返报个毫秒数，报的是网络不是系统。

**写一条记忆再搜索，这里是 1.7 ms，而两个最快的检索器根本走不了这条路** —— 因为它们把索引放在内存里，加一条就得整体重建。记忆是一条条攒出来的，所以这条路径被走到的次数远多于任何一次检索。反方向也记清楚：BM25 的查询比 Amem 快五倍，而两者都远低于能被察觉的阈值。

### 每次会话的 token 开销

这个领域对外宣传的头号指标。二十轮，数字来自服务端返回的 `usage`，基准是同一段会话完全不带记忆时的开销。

| 策略 | 输入 tokens | 其中命中缓存 | **实付** | 比基准多 |
|---|---|---|---|---|
| 无记忆（基准） | 5,566 | 5,426 | 140 | n/a —— 这就是基准 |
| **Amem —— 开场写一次** | 45,726 | 44,464 | **1,262** | +1,122 |
| 每轮检索并注入 | 21,191 | 18,711 | **2,480** | +2,340 |

按名义 token 算，开场注入贵 2.2 倍；按实际计费算，**它便宜一半**，而且差距随会话变长继续拉大 —— 开场注入是**稳定前缀**，后面每一轮都能复用；每轮往前面写检索结果会**改写前缀**，把它后面的缓存全部作废。

这一条值得所有做记忆的人注意：**按名义 token 报开销的对比，报的是错的那个数。**

### 记忆会不会随事实变更而过期

十二个会话按时间顺序写入，九条事实中六条中途被修订，最后问**当前值**。**这个领域里没有任何其他 benchmark 在测这件事**，而 mem0 在 2026-04 恰好赌了反面：放弃 UPDATE/DELETE 整合，改成单遍累积。

| 系统 | 返回当前值 | 返回已被取代的值 | 两者并列且未指明 | 从未变更的规则留存 |
|---|---|---|---|---|
| **Amem** | **6/6** | 0 | 0 | **3/3** |
| mem0(`infer=True`) | 4/6 | 1 | 1 | 1/3 |
| txtai · LlamaIndex BM25 | ✗ 它们是检索器不是记忆 —— 没有“事实被取代”这个概念 | | | |
| Cognee · MemOS · SimpleMem | — 没有在这个协议上跑 | | | |

最后一列比第一列更值得看：**三条从未变更的规则，mem0 只留住了一条**。一条不再出现的长期指令，就是一条不再被遵守的指令，而且**没有任何迹象表明它消失了**。

**而 Amem 赢这一项靠的不是为它建的那个机制**:去重一次都没触发，而且按设计就不该触发 —— 数字不同是一票否决项，而 `5494` 对 `8721` 正是这种情况。真正起作用的是**每条都带日期**，于是两个版本同时留在库里，读的人能排出先后。

### 没有 benchmark 会评分的性质

| | Amem | mem0 | Cognee | MemOS | SimpleMem | txtai · BM25 |
|---|---|---|---|---|---|---|
| 写入需要人点头 | **是** | 否 | 否 | 否 | 否 | n/a |
| 存储是可手改的纯文本 | **是** | 否 —— 向量库 | 否 | 否 | 否 —— lancedb | 否 |
| 不需要任何服务或模型即可运行 | **是** | 需要嵌入模型 | 需要 LLM | 需要嵌入模型 | 需要 LLM | 需要嵌入模型 |
| 记忆不问也会到场 | **是** | 否 | 否 | 否 | 否 | 否 |

**四行全是“是”的只有一列。** 最后一行尤其是 Amem 存在的理由：这里其余每一个系统都是**查询驱动**的 —— 你问，它找。而“对外文档里不许出现函数名”不是任何人会去问的东西，在 243 条真实发言里 **89% 是指令**，那些场景里根本没有检索发生。一个只在被问到时才工作的记忆，在你 89% 的时间里是不工作的。

### 三条比排名更有价值的发现

- **能预测准确率的，是查询时跑不跑 LLM** —— 不是存什么，也不是怎么检索。跑的那两家领先；不跑的七家在 43.0% 到 54.5% 之间、且在十个点的波动里互相分不出，而那七家里纯词法、纯向量、混合、带 LLM 抽取的都有。**那些围绕存储形式做的宣传，没有一项体现在分数上。**
- **召回转化不成答案。** 三次独立观察里，召回高出 7–11 个点的系统答得并不更好 —— 包括 Amem 自己的中文召回涨了 11 点而端到端纹丝不动。**这个领域最常报的那个指标，预测不了用户实际拿到的东西。**
- **BM25 在中文上只有 2.3%**，而英文 60.6%。这个鸿沟正是中文处理存在的理由 —— 但它的主体是一个分词器，不是这些代码：在现成 BM25 前面加五行双字切分就能到 51.3%。Amem 多出的那 7.6 个点是真的，但它不改变任何答案。

### 五个没能测成的

不是"记忆做得更差" —— 是根本没测，因为每一个都有某种东西让对比跑不起来。**这些对采用者都是实打实的代价**，所以列出来而不是省略。

| 系统 | 挡住测量的是什么 |
|---|---|
| **Graphiti** | 它的嵌入式后端不工作。十轮内容通过 Kuzu 驱动只建出 **2 个实体、0 条边**，而它的全文检索直接报错 —— 驱动从不创建它自己要查的那个索引。要按宣传的方式工作，得在你的应用旁边跑 Neo4j 和一个 JVM。 |
| **Zep** | 发的是客户端不是库。**没有本地模式**：两个包都是瘦封装，必须有服务端在跑或者有云 key，离线什么都评估不了。 |
| **Letta** | **没有把已有记忆装进去的路径**。记忆只在实时的 agent 轮次中形成，已有的历史无法导入 —— 也就无法迁移到它上面，也无法用已知的东西冷启动。 |
| **Memori** | 同样的形状：它靠拦截 LLM 调用来捕获，所以只有流经它封装的流量才会形成记忆。一份记录没法交给它。 |
| **TencentDB Agent Memory** | 三个 Node 服务加一个挡在模型 base URL 前面的代理层。那是基础设施不是依赖。 |

对 Letta 和 Memori 来说，这是**导入方式**的限制而不是**回答质量**的限制：用批量灌入去测一个在对话过程中运行的机制，本来就测不到它的长处。但它确实揭示了采用它们的一个真实约束：**一份装不进去的记忆，就是一份没法迁移、没法评估、也没法预置的记忆。**

## 两类记忆

每条记忆有一个 `kind`，而 kind 决定它以什么方式到达一次对话。

| kind | 装的是什么 | 怎么到场 |
|---|---|---|
| `user` | 用户是谁、怎么工作 | **全文陈述**，每次对话 |
| `feedback` | 一次纠正或一条长期指令 | **全文陈述**，每次对话 |
| `project` | 关于某个仓库、系统或决定的持久事实 | 索引里一行；需要时取全文 |
| `reference` | 你曾费力找到的东西在哪里 | 索引里一行；需要时取全文 |

前两类是**行为类**。它们改变 agent 的工作方式，而且从来不会成为提问的对象，所以无条件注入 —— 不管当下用不用得上，都占着上下文。

后两类是**查阅类**。其中大多数对任何一次具体对话都无关，把它们全都随身带着，比偶尔去取一次正确答案更贵。它们以一行摘要的形式出现在索引里 —— 足够让人知道“记过这件事” —— 全文按需取回。

这就是全部架构。下面所有内容，都是为了让这两半各自成立。

## 一条记忆是怎么产生的

```
  对话 ──▶ 抽取 ──▶ 候选队列 ──▶ (有人点头) ──▶ 入库
            │                          │
        你的模型                   唯一的入口
```

**抽取**每次会话跑一次，跑在本来就要生成摘要的地方，所以代价是一次调用而不是每轮的开销。提示词里有三件事值得写下来：

- **正文是嵌在提示词里的，不是追加在后面的。** 如果把对话放在最后，模型会把自己的最后一轮当成待续的那轮然后接着写下去 —— 去回答那份记录，或者发出记录里正要发出的那个工具调用。六个真实会话上实测：**每次产出的可用提案都是零**。把正文用标签围起来、任务说明放在它之后，同样六个会话每个产出四到五条。
- **事实自带日期。** 写"2026-05-06 用户把采样率估计改成了 EWMA"，而不是"采样率用 EWMA"。条目本身有 `created_at`，但那回答的是另一个问题 —— 它**被写下来**的时间，不是它**成立**的时间。
- **常见的答案是"没有"。** 提示词这么说，模型也照做：一份纯排错的记录几乎产不出东西，闲聊一条都产不出，而把上限从五条提到十二条几乎不改变数量。

**候选不是记忆。** 它们待在一个队列里，以"尚未批准"的身份展示，没人决定就会过期。`suggest()` 入队，`keep()` 提交 —— 两个分开的调用，好让这个区别没法被一个开关抹掉。

**直接写入**也存在 —— `store.add()` —— 用于用户直接说出来的事实。模型**推断**出来的东西才走队列。

## 库长什么样

```jsonl
{"id":"4f2a…","kind":"feedback","scope":"persistent","content":"不要 force-push 到 main。","created_at":1767225600.0,"key":"git/force-push"}
{"id":"91c7…","kind":"project","scope":"persistent","content":"2026-06-03 起 Windows 端口从 5494 改为 8721。","created_at":1780531200.0,"key":"win/port"}
```

一行一个 JSON 对象，基本只追加。你可以 `grep` 它、`git diff` 它、用编辑器打开改个错字，也可以靠读它来知道自己的 agent 记了些什么。这是一条设计承诺而不是存储细节：**一份你没法检查的记忆，就是一份你没法纠正的记忆。**

`key` 是一个简短的语义把手 —— `命名空间/名字` —— 模型能读懂它、能按前缀归组、打错了也看得出来。`id` 仍然是主键，因为它写进了每一条存下来的记录；`key` 是模型用来指称某一条的东西。任何接受 handle 的地方，都接受 key、完整 id，或者不产生歧义的 id 前缀。

搜索索引是一个**缓存**:库文件旁边的一个 SQLite 数据库，文件一变就重建。删掉它的代价只是一次重建 —— 而这正是让库能保持成一个人可以手改的文件的前提。

## 检索是怎么工作的

两套机制，由查询的文字系统决定谁主导。

**索引**是 SQLite FTS5，用 `trigram` 分词器。默认的 `unicode61` 按非字母数字切分，而中文不带空格 —— 一整句会变成一个 token，任何针对句中短语的查询都会落空。

**扫描**是对条目做加权子串匹配，它存在的理由是：中文里最有意义的单位是两个字 —— 邮箱、配置、路径 —— 而这**低于**三元组索引能容纳的粒度。

两个都需要，而且哪个都不够：

```
查询含中文  →  加权扫描主导，索引补剩余名额
查询纯拉丁  →  索引主导，与原来一致
```

在翻译版 LoCoMo 上测量：中文场景下，索引单独用在深度 8 上是 40.1%，加权扫描单独用是 58.9%;拉丁文场景下索引是更好的排序器。**按查询逐条选择**，正是让中文这条路提升而英文那条一点不受损的原因。

### 扫描为什么要加权

按“命中了几个 needle”排序，会让一个问句的**语法**和它的**主题**一样值钱。「邮箱是怎么配置的」的每一个双字窗口都是一个 needle，于是「是什」「什么」和「邮箱」「配置」计分完全相同，含“什么”的条目会排在含答案的条目前面。

英文有停用词表挡着这件事。中文没有，而为每种语言维护一张表是打不赢的仗。改为按**逆文档频率**给每个 needle 加权 —— 看它在**这个库里**能把范围缩小多少。语法在这里很常见，于是不再计分；主题很罕见，于是决定顺序。不需要词表，而且它会自动适应这个库讲的是什么。

仅这一处改动，中文召回@8 从 47.7% 到了 58.9%。

### 它为什么还能快

子串扫描是线性的 —— 在记忆最初设计的几十条规模上没问题，到两万条就是接近一秒。两件事在不改变“什么能匹配上”的前提下解决了它：

- **对条目双字建倒排表。** 文档频率变成一次行计数，候选也从同一次查表里出来，于是一次查询根本不会碰到那些不可能匹配的条目。
- **增量索引。** 索引原本是“库一变就整体重建”的 —— 而库每写一次就变，所以加一条记忆会让下一次搜索把所有东西重新索引一遍。

在两万条上：一次中文查询从 66 ms 到 9.8 ms，写一条之后再搜索从约 756 ms 到 50 ms。

两条路径共用同一个排序函数。当它们各有一份打分代码时，在 197 个真实问题里有 96 个结果不同 —— 同样的权重换个顺序相加，浮点误差就能把并列项排反，而其中一次排反正好把正确答案挤出了前八。有测试逐条断言两者一致。

## 写入时怎么处理重复

新增一条复述已有内容的事实，不会产生第二条：它会并入已有那条，并报告自己覆盖掉了什么措辞，好让一次错误的合并能在同一轮里撤销。

光有相似度不足以做这个判断，所以在分数**之外**还有三道守卫。每一道挡住的都是“字面几乎相同、意思完全不同”的一类：

| 守卫 | 挡住的是什么 |
|---|---|
| **长度比** | 一条详尽的记录被一句敷衍的重述替换掉。合并永远只丢弃较旧的文本，所以丢细节才是那个伤害。 |
| **数字多重集** | 日期、版本、端口、配额、工单号 —— 精度最高的一类事实，也是被静默覆盖后最难察觉的一类。 |
| **否定极性** | 语义反转。比的是**极性**而不是“有没有否定词”，所以两个都含“不带尾部总结”的变体不会被自己的“不”挡住。 |

促成第二道守卫的那个案例：`"合并冻结从 2026-03-05 开始"` 对 `"…从 2026-03-05 起开始"`（该合并）与对 `"…从 2026-04-05 开始"`（绝不能合并）。**两者得分完全相同，都是 0.967。** 阈值分不出它们；把数字当作多重集来比就能分出。而之所以比**多重集**而不是按位置比，是因为这样插入一个介词仍然能合并。

## 库怎么才不会越用越贵

行为类记忆不管相不相关都会被注入，而所有这类记忆总共约有八千字符的空间 —— 大概五十条短规则，或者十四条段落长度的。超过上限之后最老的就不再到场，而**一条不再到场的长期指令，就是一条不再被遵守的指令**，并且没有任何迹象表明它消失了。

三个机制盯着这件事。三个都只提建议，一个都不自己动手。

**取代** —— 一条新记录替换了一条旧的。三种捕捉方式，因为条目有两种形态、而修订通常会自我宣告：一句话的规则被更精确地重述，由序列相似度捕捉；多步骤的流程被改写则保留主题、改变措辞，由共享词汇捕捉；而"改用 EWMA，不再维护 48 小时窗口"这类说法是直接**陈述**了这个关系。宣告是三者里最有力的，需要的共享主题也最少。

宣告替换的惯常写法就是**否定被替换的那个**，而那恰好是否定守卫要拒绝的 —— 所以判断否定极性时会先去掉宣告用语。于是"改用…不再维护…"能配上，而"总是先跑迁移"对"从不先跑迁移"（它什么也没宣告）仍然配不上。

**休眠** —— 主题已经好几个月没出现过的条目。注意它**不**测量什么：这条规则有没有被用过。规则是靠**不做某件事**来遵守的，所以一条被恪守了一年的禁令，留下的痕迹和一条没人记得的一模一样；按"被使用"打分会**最先淘汰禁令** —— 那恰恰是最不该丢、也最不容易被察觉丢失的一类。

**压力** —— 预算被占用了多少，在 75% 时提出而不是到上限才提，因为一个等到溢出才响的信号，响的时候条目已经不再到场了。**超过 80% 之后**建议不再是"合适的时候提一下"：温和的那个版本实测下来什么也没发生 —— 一个真实的库在 83% 停了几个星期，清单每次会话都在，一次都没被提起。

但催得更紧只有在**答复能被记下来**时才成立，否则同一对会永远回来，而一个无视答复的提示只会教人不再答复。所以答复有两种：退役旧的那条，或者**确认**它 —— 两条都仍然有效。确认解决的是"当时那个库"的问题；之后写下的条目会让它重新被提出。

而且确认常常是对的那个。后来的指令通常是在旧的之上**补充**，它没写到的部分仍然是要求 —— 在一个真实的库上，同一条规则的第三代丢掉了前两代带着的三项要求，照建议退役会把它们无声地抹掉。这种情况该合并：

```python
store.consolidate(合并后的文本, replacing=["reports/v1", "reports/v2"])
```

它先写后退役：写完被打断留下一条看得见的重复，反过来被打断留下的是要求已经消失。

### 时效性靠日期解决，不靠合并

值得直说，因为它和设计时的预期正好相反。

在十二个会话、六条事实被修订的测量里：去重**一次都没触发**，而且按设计就不可能触发 —— 数字不同是一票否决，而 `5494` 对 `8721` 正是这个形状。让每个回答都是当前值的，是**两个版本都留在库里，而且各自带着日期**，于是读的人能排出先后。

这让归并的定位变了。它不是用来保持库**正确**的 —— 日期做了那件事。它是用来保持库**负担得起**的，因为每一次修订都留下两条，而变更越频繁，上限来得越快。

## 它刻意不做的事

下面每一条都被建过或测过，然后被否掉。数字（包括 Amem 输掉的那些）在 `benchmarks/`。

**不加嵌入模型。** 同一个库、同一批发言、同一个判分器：稠密检索两次得 18.1% 和 13.7%，词法是 14.0% 和 15.3%。区间完全重叠，两次运行的排序还翻转了 —— 差异小于判分器自身的波动，代价是 183 MB、建库慢 150 倍、查询慢 25 倍。

**不建知识图谱。** 把多条事实合成为一个答案是真优势，端到端领先的那些系统正是这么赢的。但统计一位用户真实历史里被问过的问题，需要组合两条以上的大约占 **1%** —— 为一种几乎不出现的问题形态做一个大工程，不划算。

**不做每轮自动注入。** 实测：**注入内容里约 85% 帮不上忙**，而且每轮都要付。有相关记忆的轮次占 64%，但检索只在其中三分之一里找得到，而没有任何字面阈值能把两者分开 —— 漏掉的是语义问题，而语义正是上一段排除掉的。代价还不止如此，且只在账单上看得见：每轮往前面写会**改写提示词前缀并作废其后的缓存**，而开场写一次的前缀会被后面每轮复用。二十轮下来，每轮检索用了一半的名义 token，实付却是两倍。

**不做自动退役。** 检测就在这里，且只用来提建议。退役一条仍然生效的规则，会改变 agent 的行为却没有任何迹象；留着一条过期的，代价是一行上下文。两者代价不对称，所以这个决定不自动做。

## 怎么用

需要 Python 3.11 或更新。只有一个依赖，pip 会自动装上：

```bash
pip install git+https://github.com/goldenxingxing/Amem
```

还没发到 PyPI —— 名字占住了，但在 API 还可能变动期间不发包。要依赖它就锁一个 commit。

### 完整接入

四个调用点。下面**不是示意，是一个完整的宿主**：它是照着全新安装写完跑通的，一共二十三行，因为其余的事这个包自己做了。

```python
import amem

store = amem.Store("~/.myagent/memory")          # 路径是你的；`~` 会被展开

# 1. 开场。不需要查询 —— agent 最需要知道的那些事，恰恰是没人会想到去问的。
def opening_context() -> str:
    return amem.render(store.entries(), store.recent(), store.pending())

# 2. 一个工具。操作是校验过的数据，执行也包含在内；
#    留给你的是"要不要先问一句"。
async def memory_tool(payload: dict) -> str:
    try:
        op = amem.parse_operation(payload)
    except amem.UnknownOperation as exc:
        return f"error: {exc}"                    # 会列出真实存在的操作
    if op.writes and not await ask_the_user(op.describe()):
        return "declined"
    return amem.execute(store, op).model_dump_json(exclude_defaults=True)

# 3. 结束。抽取只负责注意到，决定权在人。
async def on_session_end(transcript: str, complete) -> None:
    store.suggest(await amem.propose(complete, transcript))
    store.note_topics(transcript)                 # 供休眠排序使用
    append_summary(store.directory / "recent.jsonl", summary_of(transcript))

# 4. 你的批准方式。对话框、命令行、一条策略 —— 这个包对此没有意见，
#    也没有办法替你回答。
async def ask_the_user(what: str) -> bool: ...
```

`complete` 是你的模型。任何符合 `async (system, user) -> str` 的东西都行；这里不 import 任何客户端，也不读任何环境变量。

### 那些操作

`parse_operation` 校验，`execute` 执行。十二个动词，每个对应一个 `Store` 方法，所以接了这个函数的宿主**不需要自己再定义一套 schema**：

- **`search`**、**`get`**、**`list`** —— 读
- **`add`** —— 用户直接说出来的事实，没什么可批准的
- **`promote`**、**`dismiss`** —— 队列：从提案变成记忆的唯一通道
- **`update`**、**`delete`** —— 改或删
- **`retire`**、**`restore`** —— 移出开场注入但不丢失
- **`affirm`** —— 这条仍然有效，那个"不是退役"的答复
- **`consolidate`** —— 合并成一条，把每条说过的都保住

`op.writes` 说明这个操作会不会改动库，所以**要在写入前征询的宿主不必自己维护一张表**，也就不会在这个包新增动词时落后。`affirm` 在这里故意报 `False`：它不存事实也不删事实，只记录一个问题被回答了，而让人批准"记下他自己的答复"是个没有出口的循环。

不走操作层也是同样的调用：

```python
store.add("project", "日报写在 output/reports/daily/ 下。", key="reports/daily")
store.search("日报写在哪个目录")
store.get("reports/daily")                # 用 key、id 或不产生歧义的 id 前缀
store.keep(candidate_id)                  # 只在有人点头之后
```

### 让它不越用越贵

库会填满，条目会不再成立，而这些**一个都不自己动手**：

```python
fit, held = amem.pressure(store.entries(), amem.BEHAVIOURAL_BUDGET_CHARS)
amem.find_superseded(store.entries())     # 被新条目取代的旧条目
amem.find_dormant(store.entries(), now=time.time())

store.affirm("reports/daily")             # 提过了，而且它仍然有效
store.consolidate(合并后的文本, replacing=["reports/v1", "reports/v2"])
store.retire("api/version")               # 移出开场注入，但仍在文件里
```

**当新条目是在复述旧条目时，优先用 `consolidate` 而不是 `retire`。** 后来的指令通常是在旧的之上**补充**，它没写到的部分仍然是要求 —— 在一个真实的库上，同一条规则的第三代丢掉了前两代带着的三项要求，照建议退役会把它们无声地抹掉。

### 如果你跑在服务端

有两处默认取自当前进程，这在桌面上是对的，在请求处理里是任意的：

```python
await amem.propose(complete, transcript, today=用户当地日期)
await amem.propose(complete, transcript, prompt=你自己的模板)
```

`today` 是模型解析"上周二"的基准，而它会被写进一条比对话活得更久的事实里 —— **一台 UTC 的服务器和一个上海的用户，每天有好几个小时对"今天是哪天"看法不一致**。`prompt` 留给领域、语言或"什么可以被记录"的规则是自己那一套的宿主；它必须接受 `{conversation}` 和 `{today}`，而为了改一段话去复制那个函数，就是 fork 的开始。

### 你用哪种文字

检索按**书写方式**而不是按语言来处理:分词的文字 —— 拉丁、西里尔、希腊、阿拉伯、希伯来、谚文、天城文 —— 按整词匹配;连写的文字 —— 汉字、假名、泰、老、高棉、缅甸 —— 按字符窗口匹配，因为没有别的东西可切。

以前这里只有汉字和 ASCII，其余全部产生零个可搜索的词:**一句韩语或俄语的查询会静默返回空**，而条目就躺在库里。纯假名的日语也一样 —— 之前看起来能用的日语，是靠句子里的汉字过的。

## 如果没有人来批准

批准这道闸是这里唯一别人都没有的东西，所以值得把它需要什么说准 —— 它需要的**不是界面**。它需要一个人做决定，而在 agent 里，做决定的地方就是对话：`render` 把待批准的提案放进开场上下文，agent 在相关的时候提出来。这中间不涉及任何 UI，这里也不提供。

**刻意没有"替你批准"的开关。** 不是做不到 —— 三行而已，而且它们属于你的代码：

```python
for candidate in await propose(complete, transcript):
    store.suggest([candidate])
    store.keep(candidate.id)          # 无人值守：不会有人被问到
```

差别不在能力，在于**这个决定被记在哪里**。这样写出来，它是一行审查者看得见、能反驳、能删掉的代码。作为默认值，它就是所有从没去看过的人的实际行为，而本项目相对其他方案唯一能声称的那一栏，会悄悄变得和别人一样。

没人决定也不会堆积：提案上限十二条，两周过期。一个没人清的队列是此后每次会话的噪音，而一条两周没人理会的提案，本来也不值得理会。

### 让 agent 知道能调什么

开场注入会告诉 agent 怎么处理它描述的东西，所以措辞必须指向你的宿主里真实存在的东西：

```python
render(entries, recent, pending, actions=Actions(
    search='`Memory({"op": "search", "query": "<query>"})`',
    promote='`Memory({"op": "promote", "id": "<id>"})`',
    ...
))
```

默认值用的是这个库自己的方法名 —— 你直接驱动 store 时它是对的，你有工具层时它是**看得出来的近似**。这是两种失败里较好的那种：以前它写死某个应用的工具名，读起来像权威，而在别处全是错的。

## 怎么确认它真的在工作

这里每一种失效都是安静的。抽取没找到东西，看起来就像一次没什么值得记的对话 —— 而那是常见且正确的答案。检索没命中，看起来就像库里没有。这些都不抛异常，是故意的：记忆系统不该弄坏它所依附的东西。代价就是**你没法靠观察分辨"在工作"和"根本没接上"**。

```bash
python -m amem check ~/.myagent/memory
```

**能力**是关于这台机器的 —— 索引建不建得起来、往临时目录里写一条再搜回来行不行（分词文字和连写文字各测一次）。它不碰你的任何东西。**证据**是关于你这个库的：有会话摘要说明有东西在调结束钩子，有待批准提案说明抽取跑过，有主题戳说明对话被传回来过，有条目说明有人批准过。

它**不会猜**。"抽取没找到"和"抽取根本没被调用"产生的库一模一样，所以它把两种读法都说出来，并告诉你用什么办法把它们分开 —— 而不是挑一个说，那正是整个设计要避免的错误。

## 设计上的承诺

这些是**约束**而不是偏好。每一条都是 Amem 愿意为之牺牲性能的东西。

| | |
|---|---|
| **除标准库外没有依赖** | `sqlite3` 随 Python 发行。检索不再加任何东西；pydantic 是唯一的引入，用于文件边界上的校验。 |
| **库是一个文本文件** | 可 grep、可 diff、可编辑、可纳入版本管理。索引是一个会自动重建的缓存。 |
| **没有批准就不写入** | 抽取产生的是候选。候选是提案。 |
| **什么都不销毁** | 被取代的条目是**退役**:移出注入集合，仍在文件里，仍可检索，可以恢复。 |
| **模型是你的** | Amem 从不 import 任何 LLM 客户端。有测试断言这一点。 |
